# M4: campaigns, members, invites and permission checks

Goal: logged-in users can create campaigns, see "my campaigns" on the dashboard, and open,
edit and manage a campaign according to the permission matrix (DESIGN §5.3). A GM can invite
people with a link. Anyone opening the link joins the campaign, after registering if they have
no account yet.

The APIs below were checked in a scratch copy of the project on 2026-10-13:

- transactions (`db.begin()`, `&mut *tx`, `tx.commit()`)
- `Path<i64>` and `Path<(i64, i64)>`
- `OptionalFromRequestParts` for `Option<CurrentUser>`
- a feature module returning its own `Router<Arc<AppState>>`

M4 is split into two parts, each of which ends in something that runs:

- **Part A**: campaigns and permissions.
- **Part B**: members, invites, and registration through an invite.

**Scope decisions:**

- `description_md` is stored as-is and shown as **plain, escaped text** until M5 adds Markdown
  rendering.
- `archived_at` stays in the schema, but archiving waits until it's needed.
- The `sqlx::Type` enum listed for M4 in DESIGN §10 fits M6 better, where votes are
  yes/maybe/no. M4's enum is a Rust-only one, see topic 2.

## The topics, and the Rust tools for each

### 1. Feature modules and nested routers

```
src/campaigns/mod.rs        # pub fn router() -> Router<Arc<AppState>>
src/campaigns/model.rs      # Campaign, Role, Access
src/campaigns/db.rs         # queries
src/campaigns/handlers.rs   # HTTP handlers
```

- `main.rs` stops growing:
  `.nest("/campaigns", campaigns::router())`. Inside the module, routes are written relative to
  that prefix, like `.route("/{id}", get(show))`. It's like a Flask blueprint or a FastAPI
  `APIRouter` with a `prefix`.
- **`Router<Arc<AppState>>` is a generic type.** The type parameter says which state the router
  expects, and it's still unfilled. `.with_state(...)` is called **once**, in `main.rs`, on the
  outer router. It fills in the state for every nested router too.
- The dashboard handler (`index`) can move to `src/dashboard.rs`, or stay in `main.rs` for now.
  Your choice.

### 2. Permissions: an enum, a struct and `impl` blocks

Permission depends on two things: your **role in this campaign**, if you're a member, and
whether you're a site **admin**. Model exactly that:

```rust
pub enum Role { Gm, Member }

pub struct Access {
    pub role: Option<Role>,   // None = not a member
    pub is_admin: bool,
}

impl Access {
    pub fn can_view(&self) -> bool { … }
    pub fn can_manage(&self) -> bool { … }   // edit, invites, members (GM or admin)
    pub fn can_participate(&self) -> bool { … } // vote, comment (members only)
}
```

- **`impl` blocks put methods on your own types**, like methods on a Python class. Data and
  behaviour are declared separately: the `struct` holds the fields, and `impl` adds the methods.
- **`Option<Role>`** covers three cases with no `NotAMember` variant: `None`, `Some(Role::Gm)`
  and `Some(Role::Member)`. A `match` on `self.role` must handle every case, so adding a role
  later forces you to update every check. That's the Rust replacement for scattered
  `if role == "gm"` string comparisons.
- **The `matches!` macro** is a `match` that returns `bool`:
  `matches!(self.role, Some(Role::Gm))`. It's handy inside these methods.
- **Why not one enum `Admin | Gm | Member`?** An admin can also be a member of a campaign. An
  enum can be only one variant at a time, so one of the two facts would be lost. Two
  independent facts belong in two fields.
- **Non-members get a 404**, not a 403 (DESIGN §5.3). The campaign shouldn't even be
  confirmed to exist.

**The central function** loads the campaign and the access together, and every campaign
handler calls it first:

```rust
pub async fn load_for(db: &SqlitePool, campaign_id: i64, user: &CurrentUser)
    -> Result<(Campaign, Access), AppError>
```

- **It returns `AppError::NotFound`** both when the campaign doesn't exist and when the user
  can't view it.
- **It returns a tuple.** Destructure it at the call site:
  `let (campaign, access) = load_for(...).await?;`
- **Each handler then checks its own permission:** `if !access.can_manage() { return
  Err(AppError::NotFound) }`. The check sits in the handler, next to what it protects, so it's
  hard to forget.

### 3. Path parameters: `Path<T>`

- `GET /campaigns/{id}` → `Path(id): Path<i64>`. The `{id}` syntax is new in axum 0.8; older
  tutorials show `:id`.
- Two parameters are extracted as a tuple: `Path((id, uid)): Path<(i64, i64)>`.
- A non-number like `/campaigns/abc` is rejected automatically with a 400, so the parsing is
  type-driven, like `int` path converters in Flask.

### 4. Transactions

Creating a campaign is **two inserts**: the `campaigns` row, and the creator as a member.
Either both happen or neither.

```rust
let mut tx = db.begin().await?;
sqlx::query!(…).execute(&mut *tx).await?;
sqlx::query!(…).execute(&mut *tx).await?;
tx.commit().await?;
```

- **`&mut *tx`** turns the transaction into a mutable reference to the connection inside it.
  The `*` dereferences the transaction, and the `&mut` borrows the result. Each query borrows it
  mutably in turn, so two queries can't use it at the same time. The compiler enforces that.
- **There's no explicit rollback.** If a `?` returns early, `tx` is **dropped** without a
  commit, and dropping rolls it back. This is **RAII**: cleanup tied to a value going out of
  scope. It's Python's `with conn:` block, but triggered by scope instead of an indented block.

### 5. Lists: `fetch_all`, `Vec<T>` and template loops

- The dashboard's "my campaigns" is a `query_as!` into a struct, with `.fetch_all(db)`. That
  returns a `Vec<T>`, Rust's growable list.
- The template loops over it with `{% for c in campaigns %}`. Pass it as `Serde(&campaigns)`; a
  `Vec` of `Serialize` structs serializes to a list.

### 6. Form validation without a framework

- Trim the inputs and check that required fields aren't empty. On error, re-render the form with
  an `error` message and the submitted values, like login does.
- **Re-rendering with the submitted values** is easiest if the form struct derives `Serialize`
  as well as `Deserialize`. Then the whole form goes back into the template as
  `form => Serde(&form)`.

### 7. Part B: `Option<CurrentUser>`, and shared token code

- `GET /invite/{token}` works whether or not you're logged in. A handler argument
  `user: Option<CurrentUser>` needs a second trait, **`OptionalFromRequestParts`**, implemented
  on `CurrentUser`. Its function returns `Result<Option<Self>, _>`. The implementation can call
  your existing extractor and turn `Err(AppError::Unauthorized)` into `Ok(None)`.
- **The invite token** uses the same random-hex code as session tokens. Move that code into a
  small shared function, `auth::token::generate()`, instead of copying it.
- **Registering through an invite** reuses `password::hash`, `session::create` and the cookie
  code from login. The user insert, the membership insert and the `use_count` increment go in
  one transaction.

## Step 1: your task

Write one migration, `sqlx migrate add create_campaigns`, with both tables. The columns are in
DESIGN §4. Decide these yourself:

1. **`gm_user_id` and `created_by` reference `users`.** What should happen to a campaign when
   its GM's account is deleted?
   - `ON DELETE CASCADE` deletes the whole campaign.
   - `RESTRICT`, or no `ON DELETE` clause at all, refuses to delete the user while the
     campaign exists.
   - `SET NULL` needs a nullable column.
2. **`campaign_members` needs one foreign key to `campaigns` and one to `users`.** Which
   `ON DELETE` fits each? Compare with `auth_sessions`.
3. **Which columns are `NOT NULL`?** Remember that each nullable column becomes an `Option<T>`
   in Rust. `tagline` and `description_md` could be `NOT NULL DEFAULT ''` instead of nullable.
   Which do you prefer, and why?
4. **Indexes.** The primary key `(campaign_id, user_id)` makes "members of campaign X" fast. The
   dashboard asks the opposite question, "campaigns of user Y". Does that need an index?
5. **Should the GM's membership row be enforced in SQL?** A `CHECK` can't do this. Who
   guarantees that the GM is also in `campaign_members`? (Hint: topic 4.)

Then run `sqlx migrate run` and check the result with `sqlite3 data/dev.db '.schema campaigns'`.

## Step 9: instructions

The frontend is done: `templates/campaigns/members.html`. The **Members** button on the campaign
page is shown to every member. Do 9a and 9b first and get them reviewed; 9c–9e each have a
security detail worth its own review.

### Template contract (`campaigns/members.html`)

| Variable | Content |
|---|---|
| `current_user`, `campaign`, `can_manage` | as on the campaign page |
| `members` | list of `{ user_id, username, display_name, joined_at }` |
| `invites` | list of `{ id, token, expires_at, max_uses, use_count }`: only usable ones (not expired, not used up). An empty list when `can_manage` is false. |
| `error` | optional string, shown at the top |

### Routes

| Route | Sent by | Who | Success response |
|---|---|---|---|
| `GET /campaigns/{id}/members` | link | any member, admin | the page |
| `POST /campaigns/{id}/invites` | form, field `max_uses` | GM, admin | 303 back to the members page |
| `DELETE /campaigns/{id}/invites/{invite_id}` | htmx | GM, admin | empty **200** (htmx removes the row) |
| `DELETE /campaigns/{id}/members/{uid}` | htmx | GM/admin, or yourself | removing someone else: empty **200**; leaving: header `HX-Redirect: /` |
| `POST /campaigns/{id}/gm` | form, field `user_id` | GM, admin | 303 back to the members page |

**Status codes** (see DESIGN §6):
- **A validation error the user should see:** a **200**, with the page re-rendered and `error`
  set.
- **Not allowed, missing, or a crafted request:** `AppError::NotFound`, which is a **404**.
- **htmx and errors:** htmx doesn't swap 4xx/5xx responses, so a failed delete just leaves the
  row in place.
- **Use a 200, not a 204, for the deletes.** htmx 2 skips the swap on a 204, so
  `hx-swap="delete"` would never remove the row.

### 9a. `GET /campaigns/{id}/members`

**Types (`model.rs`):**
- **`Member`:** `#[derive(serde::Serialize)]`, with `user_id: i64`, `username: String`,
  `display_name: String` and `joined_at: String`.
- **`Invite`:** `#[derive(serde::Serialize)]`, with `id: i64`, `token: String`,
  `expires_at: String`, `max_uses: i64` and `use_count: i64`.

**Queries (`db.rs`):**
- **`members(db, campaign_id) -> Result<Vec<Member>, sqlx::Error>`:**
  - `campaign_members` joined to `users`, filtered by campaign and ordered by `display_name`.
  - Write the `id` column as `u.id AS user_id`. `query_as!` maps columns to fields by name.
- **`invites(db, campaign_id) -> Result<Vec<Invite>, sqlx::Error>`:**
  - Filter by campaign, plus `expires_at > strftime('%Y-%m-%dT%H:%M:%SZ', 'now')` and
    `use_count < max_uses`.

**A shared render helper (`handlers.rs`, private).** Several handlers' error paths re-render this
page, so it lives in one function:

```rust
async fn render_members(
    state: &AppState,
    user: &CurrentUser,
    campaign: &Campaign,
    access: &Access,
    error: Option<&str>,
) -> Result<Html<String>, AppError>
```

- **Loading the invites:** only managers see them. Both branches of the `if` must have the same
  type, `Vec<Invite>`:
  ```rust
  let invites = if access.can_manage() { db::invites(&state.db, campaign.id).await? } else { Vec::new() };
  ```
- **The error:** pass it as-is. `None` becomes `none` in the template, so `{% if error %}` is
  false.

**The handler `members_page`:**
- Call `load_for`. It already returns a 404 to anyone who can't view the campaign, and every
  member may see this page.
- Then:
  ```rust
  Ok(render_members(&state, &user, &campaign, &access, None).await?)
  ```

### 9b. `POST /campaigns/{id}/invites`

**The form struct:** `#[derive(serde::Deserialize)] pub struct InviteForm { pub max_uses: i64 }`.
`Form` parses `"3"` into an `i64`. Text like `"abc"` is rejected with a 422 before your handler
runs.

**`db::create_invite(db, campaign_id, user_id, max_uses) -> Result<(), sqlx::Error>`:**
1. **Clean up first,** as `session::create` does:
   `DELETE FROM campaign_invites WHERE expires_at <= <now> OR use_count >= max_uses`. That covers
   all campaigns, which is fine.
2. **Insert:** `let token = crate::auth::token::generate();`, then the `INSERT` of `campaign_id`,
   `token`, `created_by` and `max_uses`. The column defaults fill in the timestamps.

**The handler:** `State`, `user`, `Path(id): Path<i64>`, and `Form(form): Form<InviteForm>` last.
1. **Check access:** call `load_for`, then check `can_manage`. If it fails, return
   `Err(AppError::NotFound)`.
2. **Validate the range:**
   ```rust
   if !(1..=20).contains(&form.max_uses) {
   ```
   `1..=20` is an inclusive range value, and `.contains` takes a reference.
   - **On failure:** return `render_members(...)` with `Some("Pick between 1 and 20 players.")`,
     plus `.into_response()`, because the success path returns a `Redirect`.
   - **Why bother:** without this check, `max_uses = 0` would hit the `CHECK` constraint and
     become a 500. The constraint is the safety net; the handler gives the friendly message.
3. **Create and redirect:** call `db::create_invite`, then
   `Redirect::to(&format!("/campaigns/{id}/members"))`.

**Routes:**
```rust
.route("/{id}/members", get(handlers::members_page))
.route("/{id}/invites", post(handlers::create_invite))
```

**Check 9a and 9b:**
- **As the GM:** create a link for 2 players. It appears with "0/2 used", and Copy gives a full
  URL. The link itself returns a 404 until step 10.
- **Bad input:** `max_uses = 0` (edit the `min` in DevTools) brings the page back with the error.
- **keldon** (a non-admin member) sees the member list with "Leave" next to themself, and no
  invite section.

### 9c. `DELETE /campaigns/{id}/invites/{invite_id}`: revoke

**Two path parameters:**
```rust
Path((id, invite_id)): Path<(i64, i64)>
```

**`db::delete_invite(db, campaign_id, invite_id) -> Result<u64, sqlx::Error>`** returns the number
of deleted rows:
```rust
let result = sqlx::query!("DELETE FROM campaign_invites WHERE id = ? AND campaign_id = ?", invite_id, campaign_id)
    .execute(db)
    .await?;
Ok(result.rows_affected())
```

**The security detail is `AND campaign_id = ?`.** The permission check (`load_for` +
`can_manage`) is about campaign `{id}` from the URL. Without that condition, the GM of campaign 1
could call `DELETE /campaigns/1/invites/<an invite of campaign 2>`. The check would pass for
campaign 1, and campaign 2's invite would be deleted. This is called an **IDOR** (insecure direct
object reference): every child-object query must be scoped to the parent that was checked.

**The handler:**
1. Call `load_for` and check `can_manage`.
2. Call `db::delete_invite`.
3. If it returns `0`, return `Err(AppError::NotFound)`. The invite doesn't exist, or belongs to
   another campaign.
4. Otherwise return `Ok(StatusCode::OK.into_response())`. `StatusCode` comes from `axum::http`.

**The route:** `.route("/{id}/invites/{invite_id}", delete(handlers::revoke_invite))`, with
`delete` from `axum::routing`.

**Check:**
- Revoking removes the row without a page reload, and the link disappears after a refresh too.
- The same `curl -X DELETE` with another campaign's invite id returns a 404, and that invite still
  exists.

### 9d. `DELETE /campaigns/{id}/members/{uid}`: remove a member, or leave

One route, two meanings: `uid == user.id` means **leaving**, and anything else means **removing
someone**.

**`db::remove_member(db, campaign_id, user_id) -> Result<u64, sqlx::Error>`** runs
`DELETE FROM campaign_members WHERE campaign_id = ? AND user_id = ?` and returns `rows_affected()`.

**The handler,** with `Path((id, uid)): Path<(i64, i64)>`:
1. **Load:** `let (campaign, access) = load_for(...).await?;`.
2. **Permission:** leaving is allowed for anyone (`uid == user.id`); removing someone else needs
   `can_manage`. Otherwise, return `NotFound`.
3. **The GM can't be removed, and can't leave:** if `uid == campaign.gm_user_id`, return
   `NotFound`. The template never shows that button, so only a crafted request gets here.
   - **The database guards this too.** Deleting the GM's membership row violates the composite
     FK from step 1, so it would fail. Without this check, though, it would fail as a 500 with an
     FK error in the log. The check turns it into a clean rejection.
4. **Delete:** call `db::remove_member`. If it returns `0`, return `NotFound`; that user wasn't a
   member. This also covers an admin who isn't a member trying to "leave".
5. **Respond:**
   - **Leaving:** `Ok([("HX-Redirect", "/")].into_response())`. The user can't see this campaign
     any more, so htmx sends them to the dashboard.
   - **Removing someone:** `Ok(StatusCode::OK.into_response())`.

**The route:** `.route("/{id}/members/{uid}", delete(handlers::remove_member))`.

**Check:**
- **As the GM:** remove keldon. The row disappears.
  - Re-add keldon by hand:
    `sqlite3 data/dev.db "insert into campaign_members (campaign_id, user_id) values (2, 2)"`.
- **As keldon:** Leave takes you to the dashboard, and the campaign is gone from it.
- **A crafted GM removal:** `curl -X DELETE` targeting the GM's own `uid`, with the GM's cookie,
  returns a 404. The GM is still a member.

### 9e. `POST /campaigns/{id}/gm`: reassign the GM

**The form struct:** `#[derive(serde::Deserialize)] pub struct GmForm { pub user_id: i64 }`.

**`db::set_gm(db, campaign_id, user_id) -> Result<(), sqlx::Error>`** runs
`UPDATE campaigns SET gm_user_id = ? WHERE id = ?`.

**The handler:** `State`, `user`, `Path(id)`, and `Form(form): Form<GmForm>` last.
1. **Check access:** call `load_for` and check `can_manage`.
2. **The new GM must be a member:** if `!db::is_member(&state.db, id, form.user_id).await?`,
   re-render with `render_members(...)` and `Some("The new GM must be a member of the campaign.")`.
   Your composite FK enforces the same rule in the database, but as a 500, so check it here first
   for a friendly message.
3. **Update and redirect:** call `db::set_gm`, then redirect to `/campaigns/{id}/members`.

**After the change:**
- The old GM is now a plain member. Unless they're an admin, they lose the management sections
  on their next page load. That's correct.
- The old GM may now leave the campaign. The new GM can't, until they hand the role on.

**The route:** `.route("/{id}/gm", post(handlers::change_gm))`.

**Check:**
- Hand the GM role to keldon: the badge moves.
- As keldon, the invite section appears. As abahaci (an admin), the management sections still
  show, because admins can always manage.
- A crafted `user_id` of a non-member brings the page back with the error, and the GM is
  unchanged.
